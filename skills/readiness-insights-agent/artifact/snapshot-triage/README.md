# Readiness Snapshot Triage — source

React + TypeScript + Tailwind + shadcn/ui rebuild of the readiness triage artifact, built
with the `web-artifacts-builder` toolchain and styled with the same visual system as the
`Change Impact Intake` tool, so the CM Workspace toolset reads as one family: serif
display / sans body / mono data, navy accent, jade-amber-clay status trio.

The published artifact (`../snapshot-triage.html`) is the built output of this project —
edit here, rebuild, then republish that file.

## What it does

Drop in one or several feedback exports (training evaluation, comms feedback form,
readiness assessment — .xlsx or .csv), map each source's columns to a readiness
dimension, align group names across sources, and read a segment × dimension heatmap,
a negative/neutral/positive distribution per dimension, rule-based findings, and a
comment explorer. Everything is computed client-side; no file leaves the browser. See
the skill's `SKILL.md` and this folder's parent `README.md` for the product rationale.

```
├── lib/

│   ├── spreadsheet.ts            .xlsx / CSV / TSV reading (own zip+XML reader, no SheetJS)
│   ├── profiling.ts              column profiling + role/dimension/scale guessing
│   ├── analysis.ts               pooling, group-name aliasing, the matrix, findings
│   ├── exportData.ts             CSV/JSON export shapes
│   └── downloads.ts              wraps the artifact `downloads` capability
└── components/
    ├── ui/                      shadcn/ui primitives (button, table, tooltip, …)
    └── app/                     FileDrop, SourceTable, MappingBlock, AlignmentPanel,
                                  Heatmap, DistributionBars, FindingsList, CommentsExplorer
```

The analysis/finding logic in `lib/` is a direct, tested port of the original
single-file vanilla-JS artifact — same rules, same thresholds, same wording — so the
read this page produces is unchanged by the rebuild.

## Develop

```bash
pnpm install
pnpm dev          # http://localhost:5173, hot reload
pnpm run build    # tsc -b && vite build -> dist/index.html (single file, see below)
```

**Note:** two shadcn components generated by `init-artifact.sh` (`calendar.tsx`,
`resizable.tsx`) fail `tsc -b` out of the box — a version skew between the scaffolded
`react-day-picker`/`react-resizable-panels` and their type defs, unrelated to this app.
Neither is used here, so they were deleted rather than worked around.

## Why `spreadsheet.ts` doesn't use SheetJS

The obvious choice for `.xlsx` parsing is the `xlsx` (SheetJS) package, and an earlier
version of this file used it. It was pulled back out: SheetJS's main bundle carries
ODS/XLSB support, a formula engine and legacy codepage tables this page never touches,
and alone added ~500KB minified to the artifact — enough that the platform's publish-time
validator misclassified the page and refused it outright. This page only ever needs
"read the rows out of a worksheet," so `spreadsheet.ts` reads that directly: a ~100-line
ZIP central-directory reader, `DecompressionStream('deflate-raw')` for compressed
entries, and DOM-parser reads of `workbook.xml` (sheet names), `sharedStrings.xml`
(interned text) and each worksheet's cell grid. It's the same approach the original
vanilla-JS artifact used, ported to TypeScript. Total build output dropped from 695KB to
367KB, which is what got the publish to go through.

If a future requirement needs more of the format than this covers (formulas, styles,
ODS), that's the moment to reconsider SheetJS — but budget for the size cost explicitly
rather than pulling it in by default.

## Bundling to a single file

The `web-artifacts-builder` skill's own `bundle-artifact.sh` (Parcel + `html-inline`)
fails on this project: newer Radix packages use nested custom package-export
conditions (`development`/`production`) that Parcel's resolver cannot follow, even
though the exact same packages build fine under Vite. Rather than pin older Radix
versions, the project uses `vite-plugin-singlefile` instead, which inlines Vite's own
build output (already verified working) into one HTML file:

```bash
pnpm run build    # dist/index.html is the complete, self-contained artifact
```

`vite.config.ts` sets `cssCodeSplit: false` and a large `assetsInlineLimit` so the
plugin has one script and one stylesheet to inline, both of which end up as inline
`<script>`/`<style>` tags in `dist/index.html`. No `<link>`, `<script src>`, external
font, or CDN reference remains — verified by grepping the output for `http` and finding
none, and by loading the file with no network access.

**Keep an eye on the built size.** The Artifact publish path appears to apply stricter
validation once a page grows large — see the SheetJS note above, where ~700KB tripped a
misclassification that a ~370KB build did not. There's no documented hard number; if a
future change balloons the bundle, that's a signal to check what's actually being
included (most Radix primitives are bare-bones, but chart/calendar/date libraries are
not) before assuming the platform will simply accept whatever size ships.

## Testing without a browser harness

There's no Playwright/Puppeteer in this environment. The approach that worked:
build `dist/index.html`, then programmatically append a `<script>` after the **last**
`</script>` in the file. Don't use a naive search for `</body>` to find the insertion
point — when the project used SheetJS, that string appeared literally inside one of its
bundled HTML-export template constants and truncated the real script in half; the
lesson generalizes; anchor on a tag that can't appear inside a JS string, i.e. the
close of the single inlined `<script>` block. The appended script waits for
`window.load`, constructs a `DataTransfer` with embedded base64 test `.xlsx` files,
dispatches a real `drop` `DragEvent` at the element matched by `[class*="border-dashed"]`
(not by text content, which can match an ancestor), and logs each step's DOM state to a
visible div. Run the result through `headless_shell --dump-dom` and scrape the log div.
